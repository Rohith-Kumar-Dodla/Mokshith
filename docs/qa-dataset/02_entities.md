# QA Dataset Manifest — Entities

For each collection below, the manifest lists purpose, owner, required fields, creation method, dependencies, validation rules, allowed updates, and deletion policy.

--- 
## users
- Purpose: platform actors (SUPER_ADMIN, ADMIN, VENDOR, DELIVERY_PARTNER, B2B/B2C customers).  
- Owner: Identity & Platform teams.  
- Required: name, email (placeholder), mobile (placeholder), role, passwordHash, status, isVerified.  
- Optional: companyId, addresses, metadata.  
- Creation method: deterministic fixture for admin/vendor accounts; customer accounts created by registration flows for order generation.  
- Dependencies: companies, vendors.  
- Validation: role ∈ ROLES, unique email/mobile, password hash format.  
- Allowed updates: status, addresses, profile fields.  
- Deletion policy: soft-delete via isDeleted flag (avoid physical delete).

--- 
## companies
- Purpose: corporate entities owning vendors.  
- Owner: Platform / Vendor onboarding.  
- Required: name, email, phone, address, createdBy.  
- Creation method: fixture.  
- Dependencies: none.  
- Validation: unique name/email.  
- Allowed updates: contact info.  
- Deletion policy: soft-delete; do not remove if vendors exist.

--- 
## vendors
- Purpose: vendor profiles and business metadata.  
- Owner: Vendor team.  
- Required: companyId, name, status (APPROVED/PENDING/REJECTED), contact, createdBy.  
- Creation method: fixture + approval workflow exercised via UI/API.  
- Dependencies: companies, users.  
- Validation: status workflow enforcement.  
- Allowed updates: status (via approval), profile fields.  
- Deletion: do not hard delete; mark inactive.

--- 
## categories
- Purpose: product taxonomy.  
- Owner: Catalog team.  
- Required: name, slug, parentId (optional), isActive.  
- Creation: fixture.  
- Dependencies: none.  
- Validation: unique slug/name per parent.  
- Allowed updates: status, name, images.  
- Deletion: avoid removal; mark inactive instead.

--- 
## products
- Purpose: catalog entries.  
- Owner: Catalog/Product team.  
- Required: name, sku, vendorId, categoryId, price, stock, isActive.  
- Optional: images, description, moq.  
- Creation: vendor-facing APIs (simulate via flows). Some canonical products seeded as fixtures.  
- Dependencies: vendors, categories.  
- Validation: unique sku, price ≥ 0, moq ≥ 1.  
- Allowed updates: price, stock, status, images.  
- Deletion: avoid hard delete; soft-delete flag.

--- 
## inventory
- Purpose: per-warehouse product quantities.  
- Owner: Inventory team.  
- Required: productId, warehouseId, stock, reservedStock.  
- Creation: generated from product x warehouse fixtures then updated by flows.  
- Dependencies: products, warehouses.  
- Validation: stock ≥ reservedStock ≥ 0.  
- Allowed updates: stock adjustments via inventory APIs.  
- Deletion: not typical; archive if needed.

--- 
## warehouses
- Purpose: physical inventory locations.  
- Owner: Logistics.  
- Required: name, address, regionCode, contact.  
- Creation: fixture.  
- Dependencies: addresses.  
- Validation: unique name per region.  
- Allowed updates: contact, address.  
- Deletion: rarely; mark inactive.

--- 
## orders
- Purpose: business transactions.  
- Owner: Commerce team.  
- Required: userId, items[], totals, payment method, status, shippingAddress, billingAddress.  
- Creation: MUST be generated by application checkout flows (not direct insertion).  
- Dependencies: users, products, inventory, payments, warehouses.  
- Validation: inventory reservation, price integrity, user status.  
- Allowed updates: status transitions via workflow.  
- Deletion: never hard delete; archive/soft-delete per policy.

--- 
## payments
- Purpose: record payment attempts and results.  
- Owner: Finance.  
- Required: orderId, method, status, providerMetadata.  
- Creation: generated by payment flows (Razorpay sandbox, or simulated).  
- Dependencies: orders.  
- Validation: idempotency, reconciled amounts.  
- Allowed updates: status, reconciliation metadata.  
- Deletion: no.

--- 
## shipments / logistics
- Purpose: delivery lifecycle.  
- Owner: Logistics.  
- Required: orderId, assignedDeliveryPartnerId, statusHistory.  
- Creation: generated by fulfillment flows.  
- Dependencies: orders, delivery partners, warehouses.  
- Validation: consistent timestamps, allowed transitions.  
- Allowed updates: status changes.  
- Deletion: no.

--- 
## notifications / audit / analytics
- Purpose: events & observability.  
- Owner: QA / Observability.  
- Required: referenceId, type, payload, createdAt.  
- Creation: by app flows.  
- Dependencies: varies.  
- Validation: JSON payloads, sizes limit.  
- Allowed updates: status (read/unread).  
- Deletion: retention policy only.

--- 
## reference collections (countries, currencies, tax rules, settings)
- Purpose: static lookups used across app.  
- Owner: Platform/Finance.  
- Creation: fixtures; maintained manually via versioned manifests.  
- Validation: schema per reference type.
